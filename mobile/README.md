# Bidders Nepal — mobile app

A production-ready Expo / React Native app for discovering Nepal government tender
notices. It is a real client of the live **Bidders Nepal API**; every listing, statistic,
document link and notification is derived from API responses. No sample or invented
tender data is shipped in the app.

- Home dashboard, tender exploration, full detail view, bid documents, global search,
  saved tenders, change-based alerts, government-source coverage and profile.
- Light and dark themes, custom brand mark, Android-ready (EAS) build configuration.

---

## 1. Run the app

Requirements: Node 20+, npm, and the Expo tooling that is installed with the project.
For a physical phone use **Expo Go** (all libraries used here are supported by Expo Go).

```bash
cd mobile
npm install          # install from package-lock.json
npx expo start       # scan the QR code with Expo Go, or press "a" for an Android emulator
```

Useful commands:

```bash
npm run typecheck    # TypeScript, no emit
npx expo start --web # browser preview of the same code
npm run export:web   # static web build in dist/ (served for the preview panel)
npx expo-doctor      # dependency / config diagnostics
```

The API base URL defaults to `https://bidders-nepal-api.onrender.com`. Override it without
touching source:

```bash
EXPO_PUBLIC_API_BASE_URL=https://your-api.example.com npx expo start
```

or copy `.env.example` to `.env` and edit it. Only public, credential-free configuration
belongs in this value.

## 2. Build an Android APK / AAB

The project is Android-ready. Native folders are generated by Expo (Continuous Native
Generation) — do not commit `android/` or `ios/`.

**Cloud build (no Android Studio needed):**

```bash
cd mobile
npx eas-cli@latest login
npx eas-cli@latest build:configure        # one-time, links the EAS project
npx eas-cli@latest build -p android --profile preview   # installable APK
npx eas-cli@latest build -p android --profile production # Play Store AAB
```

`eas.json` already defines:

| Profile       | Output            | Use                          |
| ------------- | ----------------- | ---------------------------- |
| `development` | APK + dev client  | native development           |
| `preview`     | APK               | sideload / internal testing  |
| `production`  | AAB, auto-increment | Play Store release         |

**Local build (Android SDK + JDK 17 installed):**

```bash
npx expo run:android --variant release
```

App identity is set in `app.json`: name `Bidders Nepal`, package
`com.biddersnepal.app`, version `1.0.0`, version code `1`. Increase
`expo.android.versionCode` (and `expo.version`) before each store release.

## 3. Live API integration

All requests go through `src/api/client.ts` (timeout, retry with backoff, typed errors,
short-lived read cache) and `src/api/tenders.ts`.

| Endpoint                        | Used for                                                        |
| ------------------------------- | --------------------------------------------------------------- |
| `GET /health`                   | API status + latency in Profile, dashboard freshness            |
| `GET /api/v1/tenders/all`       | Main feed (pending + verified), dashboard stats, facets, alerts |
| `GET /api/v1/tenders`           | Verified-only feed option (strict public listing)                |
| `GET /api/v1/tenders/{id}`      | Verified detail, with automatic fallback for pending records     |

Query parameters match the OpenAPI schema exactly: `q`, `category`, `province`,
`district`, `status`, `verification_status`, `page`, `page_size` (max 500 on `/all`,
max 100 on `/tenders`), plus `include_rejected` where relevant.

### Data handling rules that matter

- **Pending vs verified.** The API currently returns 0 verified and 174 pending records.
  The app shows both (`/all`) and labels verification state on every card and detail
  page. When the verified count is 0 the dashboard explains this explicitly instead of
  pretending the feed is verified.
- **Detail fallback.** `GET /api/v1/tenders/{id}` only returns verified records, so a
  pending notice returns 404. The app then locates the record in the public `/all` feed
  (`fetchTenderFromFeed`) rather than reporting a missing tender.
- **No duplicate tenders.** `dedupeTenders` removes repeated ids and records that share a
  notice number, or the same title + organisation + source URL.
- **Missing fields are honest.** Dates, provinces, districts, budgets, deadlines and
  documents are frequently `null` in the API. The UI displays "Not provided", "Deadline
  not published" and similar labels instead of guessing.
- **Documents.** Only URLs returned in `documents[]` or `document_url` are shown. If the
  API returns none, the document section explains that and links to the original notice.
  Documents open/download/share from the original government source.
- **No credentials.** Only public read endpoints are called. Admin tokens and passwords
  do not exist anywhere in the app.

### How dashboard statistics are produced

| Metric        | Source                                                             |
| ------------- | ------------------------------------------------------------------ |
| Total notices | `total` from `/tenders/all`                                        |
| Open tenders  | `total` with `status=open`                                         |
| Verified      | `total` with `verification_status=verified`                        |
| Pending       | `total` with `verification_status=pending`                         |
| Closing soon  | Computed from the latest loaded notices (deadline ≤ 7 days) — labelled as such |
| Categories / provinces / sources | Facet counts over the latest loaded feed window, labelled |

The feed loads up to the API maximum of 500 records per request, sorts that window
fully (newest / closing soon / oldest), de-duplicates it, and reveals it in scroll-sized
steps. "Load more" continues with the next API page. So sorting is correct across the
loaded window and the footer states exactly how many notices are loaded.

## 5. Features by screen

- **Home** — greeting, global search entry, live total, open/closing/verified/pending
  stats with source labels, pending-feed notice, province chips, category tiles,
  recently published carousel, latest notices, sources entry, pull-to-refresh.
- **Explore** — debounced search, sort (newest / closing soon / oldest), filter sheet
  (status, verification, category, province, district, organisation), active filter
  chips, infinite scrolling, empty/error/retry states.
- **Tender detail** — complete metadata, remaining-time callout, pending warning,
  description, all bid documents (open/download/share), original source, share and save,
  sticky "View original notice" action. Recently viewed tenders are cached on-device and
  shown when the API is unreachable.
- **Search** — recent searches (persisted), clear search, category suggestions, live
  paginated results.
- **Saved** — bookmark from any card, local persistence, remove/clear with confirmation.
- **Alerts** — notification preferences (new notices, closing soon, deadline changes,
  new documents, amendments) plus change detection: each check compares the live feed
  with the last snapshot stored on the device. The first run only saves a baseline; no
  fabricated notifications are ever created. No push service is used (see limitations).
- **Profile** — theme mode, saved/alerts counts, API endpoint + health check, API docs,
  cache clearing, and the independent-aggregator disclaimer.

## 8. Known limitations

- The API is hosted on free Render hosting and can sleep; the client uses a 45 s timeout
  with retry and explicit wake-up messaging.
- Alerts are in-app change detection, not push notifications. Delivering background push
  would require a notification service and a backend job; that is intentionally not
  faked.
- The API's verified feed is empty and most records lack province, district, deadline and
  document data, so those parts of the UI show their honest empty states. Province
  filters appear only for provinces currently reported by the API.
- Filter values are derived from the loaded public feed, so a filter can only offer
  values the API actually returns.
- Saved tenders, search history and notification snapshots live in device storage
  (AsyncStorage / localStorage on web). There is no account system, by design.
